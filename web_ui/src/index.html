JWT Token

Decoded Payload

A JWT (JSON Web Token) is a compact, self-contained credential that proves a user's identity. It's the industry standard (RFC 7519) used by services like Google, Apple, and Hello to transmit identity assertions between systems.

A JWT has three parts separated by dots:

  • Header: algorithm and type (here: EdDSA, meaning Ed25519 Schnorr signature via FROST)
  • Payload: the identity claims (who you are)
  • Signature: cryptographic proof that no one tampered with it

Payload fields in this prototype:

FieldMeaning
sub The Direct Identifier (DI): a unique, deterministic hash derived from blinded (app_id, iss, sub). It identifies the user for this app without revealing who they are across apps. This is the privacy innovation.
iss Issuer: who created this token (tts_prototype)
aud Audience: the app this token is for (the blinded app_id, not the plaintext client_id)
iat Issued At: Unix timestamp of when the token was created
exp Expiration: after this time, the token is no longer valid
name User's display name (profile claim from the IdP)
email User's email address (profile claim from the IdP)
picture URL to user's profile picture (profile claim from the IdP)

What does an app do with this?

The Relying Party (your app) receives this JWT and:

  • Verifies the signature using the FROST group public key (published at certs/tts_verifying.pub): this proves the token was issued by the threshold quorum and hasn't been modified
  • Reads the sub (DI) to identify the user: the DI is stable (same user + same app = same DI every time) but unlinkable across different apps
  • Checks exp to ensure the token hasn't expired

In a production system (like Hello), the JWT would carry additional profile claims depending on the requested scopes. This PoC includes name, email, email_verified, and picture claims from the Mock IdP, demonstrating how profile data flows through the privacy architecture, since profile claims travel via IB (which already sees iss/sub) without compromising the partitioned design.

In a traditional system, one server holds the private key that signs all tokens. If that server is compromised, every token ever issued (and every future token) is at risk.

FROST (Flexible Round-Optimized Schnorr Threshold Signatures, RFC 9591) splits the signing key across N participants. At least t of them must cooperate to produce a valid signature. No single participant ever holds the full key.

In this prototype:

  • N = 3 signing participants, t = 2 threshold
  • A quorum of 2 signers execute the 2-round FROST protocol (commit → sign → aggregate)
  • The result is a standard Ed25519 signature: verifiers don't even need to know it was produced by threshold signing
  • Compromising 1 signer reveals nothing about the signing key

This aligns with the privacy-by-design goal: not only is the identity tuple partitioned, but even the signing authority is decentralized.

    OIDC Authorization Code Flow + PKCE

    The Authorization Code Flow with PKCE is the recommended flow for both web and native applications. It is more secure than the Implicit Flow because the id_token is never exposed in the URL.

    How it works:
    1. App generates PKCE code_verifier (random) and code_challenge = base64url(SHA256(code_verifier))
    2. App redirects user to /authorize?response_type=code&code_challenge=...&code_challenge_method=S256
    3. AB validates params, generates an authorization code, stores it with the challenge
    4. User is redirected back with ?code=...&state=...
    5. App exchanges code server-side: POST /token with code_verifier
    6. AB verifies SHA256(code_verifier) == stored code_challenge, then runs the partitioned flow
    7. App receives { "id_token": "...", "token_type": "bearer" }
