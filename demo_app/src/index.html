When you click "Sign in with Google", a chain of browser redirects runs through the partitioned architecture:

  1. Demo App generates PKCE params, redirects to AB (HTTP :4010)
  2. AB blinds app_id via PRF, redirects to IB (HTTP :4020)
  3. IB redirects to Google for real authentication
  4. User authenticates with Google, Google redirects back to IB
  5. IB exchanges Google code, extracts iss/sub, blinds them, calls tTS
  6. tTS computes DI, signs JWT with FROST threshold signature
  7. IB stores JWT in relay, redirects to AB
  8. AB fetches JWT from relay, generates authorization code, redirects to Demo App
  9. Demo App exchanges code for JWT at AB's /token endpoint (with PKCE verification)

At no point does any single component see the full tuple (app_id, iss, sub).

The broker runs a partitioned flow where no single component ever sees the full identity tuple (app_id, iss, sub):

  • AB sees client_id (= app_id) but never sees iss or sub
  • IB contacts Google and sees iss + sub but never sees app_id
  • tTS only sees blinded (hashed) values: computes a Direct Identifier (DI) and signs with FROST threshold signatures

The sub claim in the JWT is the DI: a deterministic, app-specific, unlinkable pseudonym. The same user gets a different DI for each app.

The JWT is signed by a FROST quorum (t=2 of n=3 signers), not a single key. No single signer holds the full signing key.

Integrating with moshi works exactly like integrating with any OIDC provider (Google, Hello, Auth0, etc.). The only difference is the issuer URL.

If you use an OIDC library (recommended):

  • Set issuer to your broker's URL (e.g. https://localhost:4001)
  • Set client_id to your app's identifier
  • The library auto-discovers all endpoints via /.well-known/openid-configuration
  • Everything else (PKCE, nonce, state, token exchange) is handled automatically
